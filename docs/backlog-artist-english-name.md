# バックログ: アーティスト英語表記欄（固有名詞ローマ字化の正規化）

起票日: 2026-09-22 ／ 優先度: 中（本番は壊れていない。ただし出力先が press kit なので放置は不可）

漢字のアーティスト名・人名のローマ字化が生成ごとにゆれる。EPK はキュレーターや
音楽メディアが読む press kit なので、バンド名の綴りが揺れるのは事故に近い。
アーティスト自身が登録した英語表記を唯一の正としてプロンプトに渡す、という方向。
ここは製品判断メモ（実装指示書ではない）。着手は別途指示。

---

## 事象と実測

`夜間飛行` → `Yagan Hikou`（正しくは Yakan）。`Yakan Hikō` のようなマクロン付きも混在。
`1bea377`（EPK英訳の固有名詞補完対策）前後で claude-sonnet-5 / n=12:

| | 正しい `Yakan Hikou` | ゆれ |
|---|---|---|
| `a912075`（対策前） | 4/12 | `Yagan Hikou` ×7, `Yakan Hikō` ×1 |
| `1bea377`（対策後） | 10/12 | `Yagan Hiko` ×1, `Yakan Hikō` ×1 |

対策後も約8%は誤る。`app/api/epk/translate/route.js` の system prompt は既に
`never invent or reinterpret a spelling` と Hepburn 指定（姓→名）を持っているが、
**読みが一意に決まらない漢字名には原理的に効かない**（夜間＝やかん/やかん以外の
読みを推測する余地がある）。プロンプト強化では解けない種類の問題。

なお人名は比較的安定している（`山崎千裕 → Yamazaki Chihiro` は tagline で 4/4）。
壊れやすいのは造語的なバンド名。

## 3点セット

### 1. スキーマ

`artists` に英語表記カラムを足す。候補: `name_en`。

- 既に `artist.nameEn` という**フォーム側のフィールドは存在する**
  （`lib/pitch-prompt.js` / `app/api/pitch/route.js` が `artist.nameEn || artist.name`
  で参照している）。まず **これが DB のどこに永続化されているのかを確認する**こと。
  ピッチ入力欄由来でテーブルに列が無い可能性がある（`achievements` / `description` と
  同じ罠: これらは `artists` テーブルの列ではなく、ピッチ作成フォームの
  リクエストボディ由来だった）。
- 列が無ければ追加。DDL は Supabase SQL Editor からのみ（curl / MCP 不可）。
- 既存46件ぶんの埋め方も決める（空のまま運用開始 → 入力されたものから効く、で可）。

### 2. 登録フォーム

アーティストプロフィール編集画面に「英語表記」欄。

- 任意入力。未入力なら現行どおりモデルにローマ字化させる（後方互換）。
- プレースホルダに「例: ROUTE14band / Yakan Hikou」程度のヒント。
- メンバー個人名まで持たせるかは要判断（tagline の作曲者クレジット等で出る）。
  まずバンド名だけで始めて、必要になったら広げる方が安全。

### 3. プロンプト（EPK英訳 / ピッチ生成の両方）

**両方に入れること。** 現状この2つは別系統のプロンプトで、`1bea377` の固有名詞
ルールも EPK英訳側にしか入っていない。

- EPK英訳: `app/api/epk/translate/route.js` の `SYSTEM_PROMPT`。
  ただし**このルートは今のところ DB を読まない**（`field` と `text_jp` だけ受ける）。
  英語表記を渡すならリクエストボディに足すか、ルート側で引くかの設計判断が要る。
- ピッチ生成: `lib/pitch-prompt.js`。こちらは既に `artistDbBio` 等を引数で受けており、
  `artistDbNameEn` を足すだけで入る。
- 文言の方向: 「英語表記が与えられている場合、それが唯一の正。原文の漢字から
  ローマ字を推測してはならない」。与えられていない場合の現行ルール（Hepburn・
  姓→名・綴りを創作しない）はそのまま残す。
